# AI, interview and meeting contracts — proposed, not implemented

**Release update (2026-10-23):** The backend foundation and interview scheduling are now implemented. Use [P0_BACKEND_RELEASE_CONTRACT_2026-10-23.md](./P0_BACKEND_RELEASE_CONTRACT_2026-10-23.md) for the current endpoints and remaining provider blockers. This file preserves the earlier proposal.

The integration environment has no configured AI or meeting-provider credentials. There is no AI/chat or operational interview module in this Backend. The Prisma schema already contains `Interview` and `InterviewParticipant` with company-scoped foreign keys, and the permission registry already defines `interview.create/update/cancel/view/evaluate`; no HTTP controller or approved company-role grants use them yet. The following contracts require product approval, targeted versioned database changes where identified, provider credentials, and real provider acceptance before endpoints are exposed. No endpoint below currently returns a simulated response.

## Chat vertical slice

Proposed `POST /api/v1/ai/chat-sessions` (Bearer, active user) creates a private session with `{purpose:"CAREER_GUIDANCE"}` and returns `{id,createdAt}`. `POST /api/v1/ai/chat-sessions/:id/messages` accepts `{content:string,clientMessageId:UUID}` and returns `{id,role:"assistant",content,providerModel,createdAt}` only after a provider response is received and persisted. `GET /api/v1/ai/chat-sessions/:id` returns only the owner's session and ordered messages. The caller supplies neither `userId` nor model/provider credentials. A unique `(sessionId,clientMessageId)` key makes retries idempotent; message length, request budget and per-user rate limits prevent unbounded usage. Provider timeouts return 503 with a stable code and never fabricate an assistant answer. API logs redact prompts, provider keys and personal data.

Minimum migration: `AiChatSession(id,userId,purpose,createdAt,updatedAt)` and `AiChatMessage(id,sessionId,clientMessageId,role,content,providerModel,createdAt)`, with owner FK, unique retry key, indexes and retention policy. An outbound provider adapter uses server-only credentials, explicit model allowlist, timeout, budget and structured error mapping. Provider choice and data retention need approval before migration.

## Interview scheduling and meeting adapter

Proposed `POST /api/v1/companies/:companyId/applications/:applicationId/interviews` requires active membership and a separately approved `interview.create:COMPANY` grant. Request `{scheduledAt,durationMinutes,type,location?,meetingProvider?}` follows existing `Interview` columns and uses an RFC 3339 instant; response includes persisted interview ID and status. The application must belong to the same company, candidate participation must be authorized, times must be in the future, and overlap policy must be defined. Proposed `PATCH .../interviews/:interviewId` would add `{version,...changes}` for compare-and-swap. `HIRING_MANAGER` and `VIEWER` get no permission from their names; any role-matrix change requires separate approval.

The existing Interview and participant tables already provide company/application/member FKs and scheduling fields. A targeted additive migration would be needed for optimistic `version`, provider request/idempotency ID, external meeting ID, encrypted join URL, provider state and audit details. A `MeetingProvider` adapter has `create`, `update`, `cancel` and webhook verification methods. Persist provider fields only after a real provider success; retries use an idempotency key. Provider failure leaves an explicit recoverable state, not a fake meeting. Provider credentials, callback URL and webhook signing must be available before activation.

## Recording, transcript and summary

Recording and transcription are disabled by default. Proposed `POST .../interviews/:id/recording-consents` records each participant's explicit informed choice and policy version. Recording starts only when the approved consent policy is satisfied and a verified meeting-provider event confirms it. A transcript stores source, timestamps, speaker attribution confidence, access scope, retention expiry and revocation/deletion status. Summaries are generated only from a persisted transcript through the AI adapter and must be labeled as machine-generated, reviewable and removable. Candidate access, recruiter access, retention period and deletion procedure require product/legal approval. No consent, recording, transcript or summary API is implemented in this release candidate.

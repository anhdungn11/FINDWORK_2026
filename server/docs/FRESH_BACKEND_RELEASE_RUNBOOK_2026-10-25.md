# Fresh Backend release runbook — 25 October 2026

Use Node 20.19+/22.12+/24, PostgreSQL 17, the committed Prisma schema and nine migrations. Keep database credentials, JWT secrets and refresh pepper in an ignored local environment file; never put them in a frontend bundle, command output or Git. `DATABASE_URL` must identify the intended database and `public` schema. Set `NODE_ENV`, `PORT`, `API_PREFIX=api/v1`, and explicit `CORS_ORIGINS` for the frontend origin. Keep email delivery and payment features disabled unless separately configured and approved.

From `server`, after verifying the selected database name, use `node --env-file=<local-env> ./node_modules/prisma/build/index.js validate` and `node --env-file=<local-env> ./node_modules/prisma/build/index.js migrate status`. Apply pending migrations only to that reviewed target with `migrate deploy`. A **new empty** database then needs `prisma/seed.ts` for permissions, system roles and base reference categories. This base seed does **not** install the 2026 provincial or ward catalog. The existing guarded province and ward import entrypoints are target-specific; do not reuse their integration/development write flags against a different database or silently claim a fresh database has 3,321 wards. Review and approve a target-specific official administrative bootstrap before enabling location selection there.

The committed official province snapshot is `prisma/seed-data/vietnam-administrative-2026-10-16.json`; the ward snapshot is `prisma/seed-data/vietnam-wards-2026-10-24.json`, canonical UTF-8/LF SHA-256 `5c1f716a3ae1ab854a9d642e1bf82293999f7e66c8bb067edc6663b12ba18f2d`. After an approved bootstrap, run `node --env-file=<local-env> scripts/check-release-reference.cjs`. It is read-only and exits nonzero with `REFERENCE_DATA_INCOMPLETE` unless all 34 active province and 3,321 active ward codes, names, types and parents match the approved snapshots. A fresh database with only migrations/base seed should therefore be reported as missing reference data. Do not use another application's live ward list as proof of this local catalog.

Build with `npm.cmd run build` on Windows, then start `node --env-file=<local-env> dist/main.js` on the reviewed Backend port. Confirm `GET /api/v1/health` returns healthy database status; `GET /api/v1/reference/provinces?pageSize=1` reports total 34; `GET /api/v1/reference/wards?pageSize=1` reports total 3,321; `GET /api/v1/jobs?pageSize=1` returns `{data,pagination}`; and unauthenticated `GET /api/v1/auth/me` returns HTTP 401. For the current integration environment, the frontend API base is `http://127.0.0.1:3002/api/v1`; the browser origin must appear in `CORS_ORIGINS`. Job search supports only `sort=newest|salary_asc|salary_desc` and the filters listed in [the Antigravity API handoff](./ANTIGRAVITY_JOB_SEARCH_HANDOFF_2026-10-25.md).

Before any approved integration data write, create a new custom-format PostgreSQL dump outside the worktree, verify its SHA-256 and `pg_restore --list`, restore it into a disposable database, and compare source/restored counts.
